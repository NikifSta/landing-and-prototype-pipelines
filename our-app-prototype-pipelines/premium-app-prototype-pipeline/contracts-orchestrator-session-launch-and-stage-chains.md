# Исполнители, запуск сессий и цепочки

Правила только для оркестратора; общие правила и карта частей — [CONTRACTS.md](CONTRACTS.md).

## Исполнители и сессии

- **Авторы** — Opus 5.5 (`claude-opus-5-5`) через `claude -p` по [правилу исполнителей](../../docs/prototyping_execution_policy.md). Автор заданий дизайна этапа 16 и каждый из пяти авторов этапов 13 и 16 — новая сессия. Автор кода этапа 18 — новая сессия; он продолжает этап 19 и правки по сверке и со Стопа 5 в той же сессии по сохранённому `session_id`. Автор кода этапа 22 — новая сессия; он продолжает этап 23 и правки проверки 24. После Стопа 5 все правки кода, включая систему и экраны, делает автор 22–23.
- **Генераторы данных** этапа 12 — Sonnet 5 (`claude-sonnet-5`) с `--effort medium` через `claude -p` по тому же правилу исполнителей: новая сессия на автора каркаса и на каждого автора части. Ошибку склейки исправляет автор части в своей сессии.
- Роль, назначенная Astra, выполняется через Codex.

## Запуск сессий `claude -p`

Генераторов этапа 12 и авторов этапов 13, 16, 18, 19, 22 и 23 оркестратор сразу запускает отдельной службой `systemd-run --user`, а не фоновой задачей своей сессии: фоновая задача обрывается вместе с сессией и уносит запущенных авторов, запуск приходится повторять.

```bash
systemd-run --user --unit="<продукт>-stage-<NN>-<роль>" --collect \
  -p MemoryMax=5G -p OOMPolicy=continue -p RuntimeMaxSec=4h --working-directory="$run" \
  bash -c 'xargs -P 3 -L 1 bash sessions/run-stage-<NN>-<роль>.sh < sessions/stage-<NN>-session-ids.txt > sessions/results/stage-<NN>-launcher.log 2>&1'
```

- Одновременно — не больше трёх сессий, служба ограничена `MemoryMax=5G`: на машине 7,8 ГБ памяти и 4 ГБ подкачки, часть постоянно занята Claude Manager и, пока открыт, Chrome навигатора. Если перед запуском `free -m` показывает меньше 4 ГБ доступной памяти — не больше двух сессий (`xargs -P 2`).
- **Авторы этапов 13 и 16 — до пяти одновременно.** Перед запуском оркестратор закрывает Chrome навигатора (`stop-real-chrome-session.py` скилла `real-chrome-web-navigator`), если его не использует идущий этап; навигатор нужен только на 02 и 15 и запускается снова перед ними (`launch-real-chrome-session.py`). Число сессий — по доступной памяти `free -m` после закрытия: от 5,5 ГБ — пять, от 4,5 ГБ — четыре, иначе три; служба — `MemoryMax=6G`. Автор, завершившийся сбоем (в том числе по памяти), перезапускается один раз новой сессией после окончания остальных.
- `OOMPolicy=continue`: если одна сессия упала по памяти, остальные продолжают, а не останавливается вся служба.
- Лимит работающей службы поднимается на ходу: `systemctl --user set-property --runtime <служба> MemoryMax=<N>G`.
- `sessions/run-stage-<NN>-<роль>.sh` запускает одну сессию: модель, уровень рассуждений, `session_id`, промпт и пути результата — по правилу исполнителей.
- Завершение оркестратор узнаёт по `systemctl --user is-active <служба>`; обрыв ожидающей задачи не задевает службу. Под Claude Manager служба получает все переменные `CLAUDE_MANAGER_*` через `--setenv` и в конце вызывает `claude-manager-request-wakeup` с итогом.

## Цепочки между остановками

Все этапы между двумя остановками идут одной службой — цепочкой; проверка внутри неё — проход 1 → правки автора → проход 2 → следующий этап. Оркестратор сам в цепочке не участвует; его будят только на остановке, при сбое шага и там, где следующий этап начинается с документа оркестратора.

- **Документы оркестратора — до запуска цепочки.** `layouts/LAYOUT_MODELS.md` пишется сразу после Стопа 2 (зависит от ключевого экрана, не от данных); `windows/WINDOW_FRAMES.md` — сразу после Стопа 4. `designs/STYLE_BRIEF.md` заполняется по ответу на Стопе 2 и, если стиль сменён, на Стопе 3.
- **Состав цепочек.** После Стопа 1: 01–02 (или перенос исследования) с итогом исследования, 04, 05, 09, 10 → пробуждение для 11 и Стопа 2. После Стопа 2: 12 (каркас, части, склейка инструментом) и 15 параллельно, затем закрытие Chrome навигатора, 13 → пробуждение для предварительной сверки, галереи и Стопа 3. После Стопа 3: проверка выбранной раскладки 14 (при смене стиля — параллельно с повторным 15), затем 16 — автор заданий дизайна, затем авторы дизайнов → пробуждение для предварительной сверки, галереи и Стопа 4. После Стопа 4: проверка выбранного дизайна 17, затем 18, 19 → пробуждение для сверки экранов, галереи, файла экранов и Стопа 5. После Стопа 5: 22, 23, 24 с архивами версий → пробуждение для сверки и упаковки 25. Изменения по ответу пользователя на остановке (соединить варианты, правки экранов) — короткая цепочка по тем же правилам.
- **Решения по вердикту** — по файлу вердикта проверяющего ([правила проверок](contracts-reviews-and-result-versions.md), пункт «Файл вердикта»).
- **Сбой шага останавливает цепочку.** Ненулевой код, `is_error`, отсутствие ожидаемого выхода, неудачная повторная склейка данных после одной правки автором части — цепочка не запускает следующий шаг на сломанном входе и будит оркестратора с причиной.
- **Файлы.** Скрипт — `sessions/run-chain-after-stop-<N>.sh`; журнал шагов с временем UTC и кодами завершения — `sessions/results/chain-after-stop-<N>.log`; `session_id` шагов — `sessions/chain-after-stop-<N>-session-ids.txt`. Оркестратор переносит их в `RUN.md` при пробуждении.
