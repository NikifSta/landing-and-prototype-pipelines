# Правила исполнения и контракты

## Назначение

Это общие правила для оркестратора и всех агентов. Каждый промпт этапа читается вместе с этим файлом и частями правил из своего «Входа». Результат пайплайна — интерактивный frontend-прототип приложения для показа на лендинге.

«Студийное качество» — уровень исполнения по [app-ui-studio-quality-floor.md](app-ui-studio-quality-floor.md), а не стиль. Стиль выбирает пользователь по [app-ui-style-family-menu.md](app-ui-style-family-menu.md). Инструкции не означают, что исследование, дизайн или демо уже выполнены.

## Части правил

Правила разделены по читателю. Агент этапа читает части, перечисленные во «Входе» его промпта; оркестратор читает все части.

- [contracts-competitor-research-and-scope-mode.md](contracts-competitor-research-and-scope-mode.md) — «правила исследования»: режим охвата, исследователи, реестр регистраций, вход в сервисы, доказательства, вопросы о сервисах вне остановок.
- [contracts-reviews-and-result-versions.md](contracts-reviews-and-result-versions.md) — «правила проверок»: проходы, существенный дефект, проверка деталей, файл вердикта, закрытие замечаний, версии результатов и демо.
- [contracts-demo-data-behavior-format-and-quality.md](contracts-demo-data-behavior-format-and-quality.md) — «правила демо»: правило данных, поведение демо, формат и размер, студийное качество.
- [contracts-orchestrator-session-launch-and-stage-chains.md](contracts-orchestrator-session-launch-and-stage-chains.md) — «правила запуска сессий», только оркестратору: исполнители и модели, запуск сессий `claude -p`, цепочки между остановками.
- [contracts-orchestrator-stops-and-run-log.md](contracts-orchestrator-stops-and-run-log.md) — «правила остановок», только оркестратору: остановки, сверка оркестратора, ответы на Стопах 3 и 4, показ на странице запуска, статусы, журнал `RUN.md`.

## Папка запуска

Каждый запуск живёт в `dev/pipeline-workspace/<UTC-дата-время>-<продукт>/`; папка игнорируется Git. Файлы определяются по имени; история чата не заменяет обязательный файл.

- `RUN.md` — журнал запуска (состав — раздел «Журнал RUN.md» правил остановок).
- `product/` — `CONFIRMED_INTENT.md`, `FEATURE_MATRIX.md`, `APP_BRIEF.md`, `ENTITIES_AND_NAVIGATION.md`, `USER_FLOWS.md`, `DEMO_STATES.json`, `KEY_SCREEN_AND_DEMO_ROUTE.md`, `DATA_VOLUME_NORMS.md`, `DEMO_DATASET.json`; `dataset-parts/` — каркас, план и части данных этапа 12.
- `research/` — `RESEARCH_PLAN.md`, `services/<slug>/RESEARCH.md`, `services/<slug>/evidence/`.
- `layouts/` — `LAYOUT_MODELS.md`; `layout-01` … `layout-05/` с `key-screen.html`, `key-screen.png`, `LAYOUT_NOTES.md`; `LAYOUT_REVIEW.md` — проверка выбранной раскладки; `gallery.html`.
- `references/` — `STYLE_REFERENCES.md`, `images/REF-01.png` … `images/REF-10.png`, `CALIBRATION.md`, `DETAIL_INVENTORY.md` — список деталей зрелого экрана, `assets/` — материалы деталей (иконки, логотипы, аватары) с `ASSETS.md`.
- `designs/` — `STYLE_BRIEF.md`, `DESIGN_BRIEFS.md`; `design-01` … `design-05/` с `key-screen.html`, `assets/`, `key-screen.png`, `self-check/` — снимки проверки деталей, `DESIGN.md`; `DESIGN_REVIEW.md` — проверка выбранного дизайна; `gallery.html`.
- `windows/` — `WINDOW_FRAMES.md`; `frames/<FRAME-ID>-<slug>/window.png` — снимки экранов из приложения; `gallery.html`; `<продукт>-screens.html` — самодостаточный HTML сборки со списком кадров для Стопа 5.
- `app/` — исходный код демо с дизайн-системой и служебными страницами `#/design-system` (образец компонентов) и `#/frames` (просмотрщик кадров), `app/DESIGN_SYSTEM.md`, статическая сборка `app/dist/`, снимки самопроверки автора `app/self-check/`.
- `review/` — `DEMO_REVIEW.md`, `screenshots/`, архивы проверенных версий демо `app-pass-1.tar.gz`, `app-pass-2.tar.gz` (этап 24).
- `landing/` — `frames/`, `FRAME_MAP.md`, `DEMO_SEQUENCE.md`.
- `HANDOFF.md`.

Общие для всех запусков файлы вне папки запуска — раздел «Исследование и регистрации» правил исследования.

## Приоритет источников

Текущие явные указания пользователя → `CONFIRMED_INTENT.md` → `APP_BRIEF.md` → производные документы.

`APP_BRIEF.md` — единственный сводный источник принятых продуктовых фактов, объёма и правил. Начиная с этапа 05 он передаётся каждому автору и проверяющему целиком вместе с нужными производными документами; производные документы ссылаются на его разделы и ID, а не пересказывают продукт. Наблюдение конкурента не отменяет требование пользователя.

После Стопа 2 состав страниц и сценариев демо определяет `KEY_SCREEN_AND_DEMO_ROUTE.md`: это подтверждённое пользователем указание. Оркестратор приводит раздел «Маршрут показа на лендинге» в `APP_BRIEF.md` и пометки в `USER_FLOWS.md` в соответствие с ним.

Пробел закрывается минимальной помеченной гипотезой: основание, затронутые ID, следствие ошибки. Изменение продуктового правила возвращается в 04 с обновлением зависимых документов. Прямое неразрешимое противоречие — `BLOCKED` с точными ссылками.

## Роли

- **Оркестратор** — ведущая сессия; он же организует исследование. Единственный, кто пишет в `RUN.md`, галереи, `STYLE_BRIEF.md`, `LAYOUT_MODELS.md` и `KEY_SCREEN_AND_DEMO_ROUTE.md`. Остальные роли передают ему сведения для записи.
- **Исследователи** — по разделу «Исследование и регистрации» правил исследования.
- **Авторы и генераторы данных** работают в сессиях `claude -p`, которые запускает оркестратор. Исправления делает автор исправляемого результата в своей сессии.
- **Проверяющие** — не авторы проверяемой работы, начинают в новом контексте.

## Возвраты

- **Что переделывается.** После возврата к более раннему этапу переделываются только результаты, зависящие от изменённых ID. Выборы пользователя сохраняются; если изменение существенно затрагивает выбранную раскладку, дизайн или состав маршрута, пользователь подтверждает заново на соответствующей остановке.
- **Лимит возвратов без проверяющего.** Любой этап без проверяющего возвращает работу к одному и тому же более раннему этапу не больше одного раза за запуск; дальше — открытое замечание в `RUN.md` и продолжение. Возвраты по явному указанию пользователя не ограничиваются.

Лимит проходов проверки и повторная проверка этапа, к которому вернулись, — в правилах проверок.

## Сквозные ID

D — отличие; FEA — функция продукта; J — задача; E — сущность; IA — область; F — сценарий; ST — состояние; SCR — страница демо; REF — референс; MOOD — референс настроения от пользователя; DETAIL — деталь зрелого экрана из `references/DETAIL_INVENTORY.md`; плюс ID записей данных. Функции конкурентов в досье получают префикс сервиса: `FEA-<slug>-01`; продуктовые FEA-ID выдаёт только этап 04. Один ID сохраняет смысл между файлами.
