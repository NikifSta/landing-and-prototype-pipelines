# 12 — Подготовить данные реального объёма

**Исполнитель:** генераторы данных ([правила запуска сессий](../contracts-orchestrator-session-launch-and-stage-chains.md), «Исполнители и сессии») — сначала автор каркаса, затем авторы частей параллельно; оркестратор склеивает части инструментом. Независимой проверки данных нет.

**Вход:** подтверждённый `product/KEY_SCREEN_AND_DEMO_ROUTE.md`, полный `product/APP_BRIEF.md`, `product/ENTITIES_AND_NAVIGATION.md` с типами содержимого, `product/USER_FLOWS.md`, `product/DEMO_STATES.json`, досье исследования с наблюдёнными объёмами; [CONTRACTS](../CONTRACTS.md); [правила демо](../contracts-demo-data-behavior-format-and-quality.md), раздел «Правило данных».

**Формат `DEMO_DATASET.json`** — валидный JSON:

- `status`, `sources`;
- `context`: `language`, `locale`, `timezone`, `reference_time`, `persona`;
- `norms_ref` — путь к `DATA_VOLUME_NORMS.md`;
- `records` по E-ID — запись содержит `id`, `volume_case`, `content_depth` и свойства модели, связи — ссылками на ID;
- `scenario_fixtures`: `id`, `flow_refs`, `record_refs`;
- `state_fixtures`: `id`, `ui_area_ref`, `state_ref`, `record_refs` и/или `context` для запроса или фильтра;
- `screen_fixtures` — по одной на каждую главную страницу и вспомогательный экран из `KEY_SCREEN_AND_DEMO_ROUTE.md`: `id`, `screen_ref` (SCR-ID), `record_refs` — записи, которые страница показывает крупно, `collection_refs` — ID `state_fixtures` или записей для списков, счётчиков и боковых панелей. Отсюда этапы 13–24 берут записи страниц.

ID записей — строчные слаги (`invoice-2026-06-09-acme`); ID документов пайплайна (F-, ST-, SCR-, AREA- и другие) — заглавные. Ссылочные поля называются `<имя>_ref` (одна ссылка) или `<имя>_refs` (список). По этим соглашениям инструмент склейки находит ссылки на записи.

Стабильные ID, согласованные связи и хронология. Тексты предметные, подробные, на языке продукта; без lorem ipsum, служебных подписей и настоящих личных данных. Число записей в коллекциях следует нормам. Канонические записи не дублируются внутри fixtures.

Форма данных следует [правилам приоритета и структуры](../app-ui-content-priority-and-structure-rules.md) 4 и 6: раскладка не выносит то, чего нет в данных отдельно. Перечисление — список пунктов, а не маркеры в строке текста. Если в продукте есть сводка, её числа, даты и имена остаются в её тексте; отдельные поля фактов, повторяющие сводку, не создаются. Если продукт показывает источники утверждений, каждый пункт ссылается на свой источник полем `*_refs`; общий список источников на весь текст и служебные приписки об основаниях внутри текста не допускаются.

Данные для деталей зрелого экрана — не дожидаясь списка деталей этапа 15 (он собирается параллельно) и только для того, что есть в продукте: у людей — инициалы; у источников и подключённых сервисов — вид для логотипа (`source_kind`, `service_kind`); у аудио и видео — ряд пиков громкости для полосы плеера (`waveform_peaks`: речь или звук выше, паузы ниже, по времени содержимого); у объектов с обложкой — ссылка на обложку. Этих полей не бывает в тексте записи: деталь рисуется из поля, а не из слов.

Глубина содержимого (`content_depth`): `full` — полное содержимое по нормам у записей, которые показывают страницы и сценарии подтверждённого маршрута; `list_fields` — у остальных записей только поля, нужные спискам, поиску и счётчикам. Разброс: в каждой коллекции есть короткие, типичные и длинные записи (`volume_case`: `short`, `typical`, `long`); длинные случаи имеют `content_depth: full` и попадают на ключевой экран и страницы демо через `screen_fixtures`.

**Действия**

1. **Каркас — один автор.**
   - Персонаж и ситуация демо: кто пользуется продуктом, как давно и насколько активно. Это задаёт масштаб: аккаунт после нескольких месяцев работы выглядит иначе, чем первый день.
   - Нормы объёма — `DATA_VOLUME_NORMS.md` по пункту «Нормы до генерации» правил демо: для каждой E-ID, каждого отображаемого свойства и коллекции; основание нормы — с меткой «наблюдение» (evidence-ID из досье), «знание предметной области» или «оценка».
   - `product/dataset-parts/skeleton.json` — набор в формате выше со всеми записями верхнего уровня и сквозными записями: ID, связи, даты, названия, `volume_case`, `content_depth` и краткое содержание, на которое опираются части; все fixtures. Поля, которые допишут части, в каркасе отсутствуют — без заглушек.
   - `product/dataset-parts/PARTS_PLAN.md` — от двух до четырёх частей. Часть — независимая ветвь данных: записи каркаса, которые она дописывает, и вложенные записи, которые она создаёт, с уникальным префиксом ID части. Связное содержимое (например, документ, его разделы и комментарии к ним) лежит в одной части. Для каждой части — что она обязана упомянуть, чтобы совпасть со сквозными записями каркаса.
2. **Части — авторы параллельно, по одному на часть.** Каждый получает эти входы, каркас, план и номер своей части и пишет `product/dataset-parts/part-<slug>.json` с полем `records` по E-ID:
   - новые вложенные записи своей части;
   - дополнения записей каркаса: та же `id` и только новые поля;
   - в сквозную запись каркаса, которая перечисляет записи нескольких частей, — дополнение с той же `id` и ID своих записей в поле `*_refs`; списки частей объединяются при склейке.

   Часть ссылается только на записи каркаса и свои. Fixtures часть не меняет; недостающие записи fixtures — вопрос к оркестратору.
3. **Склейка — оркестратор:**

   ```bash
   .venv/bin/python dev/pipelines/premium-app-prototype-pipeline/tools/demo_dataset_parts_merger.py \
     --skeleton "$run/product/dataset-parts/skeleton.json" \
     --parts "$run"/product/dataset-parts/part-*.json \
     --output "$run/product/DEMO_DATASET.json"
   ```

   Инструмент объединяет записи и не пишет файл, если две части задали одному полю разные значения, ID повторяется или ссылка ведёт на несуществующую запись; сообщение называет часть, запись и поле. Ошибку исправляет автор этой части в своей сессии (`--resume` по сохранённому `session_id` с той же моделью), затем склейка повторяется.

**Выход и потребитель:** `product/DATA_VOLUME_NORMS.md`, `product/DEMO_DATASET.json`; рабочие материалы — `product/dataset-parts/` → раскладки 13, дизайны 16, код 18–19 и 22–23, проверки 14, 17, 24.

**Готовность:** Склейка прошла без ошибок; у каждой нормы есть основание; у каждой главной страницы и вспомогательного экрана маршрута есть `screen_fixtures`, у главных страниц — с длинным случаем; у записей `screen_fixtures` пункты перечислений и — если продукт их показывает — источники лежат отдельными полями.

**Возврат:** Нет нужного отображаемого свойства → 05 с обновлением зависимостей; условие состояния → 10; состав страниц → 11, существенное изменение — с новым подтверждением; ошибка склейки → автору части. Новый продуктовый объём не создавай.
