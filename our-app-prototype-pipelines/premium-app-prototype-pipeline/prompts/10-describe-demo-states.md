# 10 — Описать состояния демо-сценариев

**Исполнитель:** UX-дизайнер состояний.

**Вход:** полный `product/APP_BRIEF.md`, `product/ENTITIES_AND_NAVIGATION.md`, `product/USER_FLOWS.md`; [CONTRACTS](../CONTRACTS.md).

**Действия**

Опиши только наблюдаемые состояния областей интерфейса в сценариях с пометкой «маршрут показа». Отдельное состояние нужно, когда меняется видимое содержимое, статус, доступное действие или следующая реакция.

Допустимые виды состояний:

- `ready` — обычная работа с данными;
- `empty` — только если пустота естественно входит в сценарий показа;
- `processing` — только если сценарий показывает видимую автоматизацию;
- `result` — полезный результат сценария.

Ошибки, блокировки, частичные и крайние состояния не проектируются: демо показывает продукт на лендинге и не реализует крайние случаи.

`DEMO_STATES.json` — валидный JSON:

- верхний уровень: `status`, `sources`, `ui_areas`, `issues` при наличии;
- область: `id`, `name`, `refs`, `default_state`, `states`, `transitions`;
- состояние: `id`, `kind`, `condition` (проверяемые факты для данных), `visible` (наблюдаемые результаты), `available_actions`;
- переход: `id`, `from`, `event`, `to`.

Для каждого действия и видимого автоматического события сценария маршрута показа есть переход. Сами записи данных создаёт следующий этап.

**Выход и потребитель:** `product/DEMO_STATES.json` → ключевой экран 11, данные 12, раскладки 13, экраны в коде 18–19, связка 22–23.

**Готовность:** JSON разбирается; ID и ссылки разрешаются; состояния и переходы покрывают сценарии маршрута показа; для каждого состояния понятно, какими данными его показать.

**Возврат:** Разрыв сценария → 09; условие или видимая реакция → здесь. Неисправимое противоречие передай оркестратору; скрытую серверную модель не создавай.
