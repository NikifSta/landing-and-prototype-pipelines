# 16 — Нарисовать пять дизайнов ключевого экрана

**Исполнитель:** автор заданий дизайна, затем пять независимых авторов дизайнов, отдельная сессия на каждого ([правила запуска сессий](../contracts-orchestrator-session-launch-and-stage-chains.md), «Исполнители и сессии»).

**Вход:** выбранная раскладка (`key-screen.html` и `LAYOUT_NOTES.md`), главный вопрос ключевого экрана из `layouts/LAYOUT_MODELS.md`, `designs/STYLE_BRIEF.md`, `references/STYLE_REFERENCES.md` с изображениями, `references/CALIBRATION.md`, `references/DETAIL_INVENTORY.md` и `references/assets/`, снимки главных рабочих экранов конкурентов из `research/services/<slug>/evidence/`, [порог качества структуры экрана](../app-ui-layout-structure-quality-floor.md), [порог студийного качества](../app-ui-studio-quality-floor.md), [правила приоритета и структуры](../app-ui-content-priority-and-structure-rules.md), описание выбранного семейства из [меню стилей](../app-ui-style-family-menu.md), `product/KEY_SCREEN_AND_DEMO_ROUTE.md`, полный `product/DEMO_DATASET.json`, полный `product/APP_BRIEF.md`, открытые замечания выбранной раскладки (правила проверок, «Проверки», пункт «После второго прохода»); при новом круге дизайнов — причины отказа из `RUN.md`; если Иван уже выбрал дизайн этого продукта в прежнем запуске — **основа** `designs/accepted-design/` (оркестратор копирует её до цепочки: страница, `assets/`, снимок, `DESIGN.md`); [CONTRACTS](../CONTRACTS.md), [правила демо](../contracts-demo-data-behavior-format-and-quality.md), [правила проверок](../contracts-reviews-and-result-versions.md). Авторам дизайнов — ещё `designs/DESIGN_BRIEFS.md`.

**Действия**

**Задания.** Автор заданий дизайна пишет `designs/DESIGN_BRIEFS.md` — пять заданий внутри одного выбранного семейства, под номерами вариантов, назначенными оркестратором в цепочке, — и проверяет их до выдачи по [правилам заданий](16-design-briefs-writing-and-check.md).

**Планка.** Эталон задаёт уровень исполнения — типографику, ритм отступов, сдержанность цвета, число элементов и цельность экрана; его фирменные приёмы (особые формы, персонажи, особый вид строк, раскладка) в задания и дизайны не переносятся.

**Дизайны.** Авторы работают независимо и не видят чужих результатов; каждый читает своё задание в `DESIGN_BRIEFS.md`. Автор рисует выбранную раскладку ключевого экрана в том же состоянии (ST-ID из `KEY_SCREEN_AND_DEMO_ROUTE.md`) в HTML высокой точности — всю страницу шириной 1440 CSS px с высотой по содержимому (правила демо, «Формат и размер»):

- из раскладки сохраняется то, что перечислено в разделе «Студийное качество» правил демо; вид строк, карточек и элементов внутри областей автор решает сам по референсам и образцам из пункта «Проверка деталей» правил проверок;
- замысел задания виден на экране, главный элемент читается первым; уровень исполнения — не ниже эталона планки задания;
- детали из `references/DETAIL_INVENTORY.md` перенесены в дизайн материалами из `references/assets/`: значки — из одного набора, логотипы — официальные, аватары — по данным; каждая пропущенная деталь — с причиной в `DESIGN.md`;
- содержимое — из записей и выборок ключевого экрана (`screen_fixtures`), включая длинный случай, по разделу «Правило данных» правил демо;
- шрифты и прочие ресурсы лежат локально в `assets/`;
- порог студийного качества соблюдается, включая требование раздела «Состояния» к HTML-дизайнам этапа 16.

Отдельные эскизы и отчёты о поиске не требуются: автор сдаёт дизайн. Перед сдачей автор один раз сверяет результат с порогом по отрисовке, снимает всю страницу [инструментом снимков](../tools/html_mockup_screenshot_capturer.py) в `key-screen.png` — по отчёту нет обрезанного содержимого и внутренних прокруток вне закреплённых зон — и сверяется с образцом по пункту «Проверка деталей» правил проверок; снимки сравнения — в `self-check/` своей папки. Последний шаг — **убрать**: автор ставит верх своей страницы рядом с эталоном задания в одном масштабе и убирает рамки, плашки, цвета и элементы, без которых экран сильнее; убранное с причиной — в `DESIGN.md` (это же причина расхождения по «Проверке деталей»).

`DESIGN.md` каждого варианта: замысел и как он выполнен; убранное на последнем шаге с причиной; пара шрифтов со шкалой кеглей; цветовые роли со значениями и слоем; плотность; поверхность и глубина; фон и цветовые пятна; фирменная деталь; детали — DETAIL-ID перенесённых и пропущенных с причиной; итог проверки деталей — части строк рядом с образцом и причины расхождений; использованные REF-ID, включая эталон планки; при правках после проверки 17 — по каждой правке уровня: внесена или почему нет.

**Выход и потребитель:** `designs/DESIGN_BRIEFS.md` → авторы дизайнов 16, сверка и проверка выбранного дизайна 17; для каждого варианта `designs/design-0N/key-screen.html`, `assets/`, `key-screen.png`, `self-check/`, `DESIGN.md` → сверка, выбор и проверка выбранного дизайна 17.

**Готовность:** Задания различаются по порогу и прошли проверку; пять HTML-дизайнов открываются целой страницей шириной 1440, следуют своим заданиям и замыслам, содержимое полное и совпадает с записями, проверка деталей записана.

**Возврат:** Исправления приходят из предварительной сверки и из проверки выбранного дизайна 17 (правила проверок, «Проверки» и «Версии результатов»).
