# Карта сборки нового процесса

Этот файл задаёт преобразование исходных документов при выполнении `MASTER_PROMPT.md`. Содержимое `source-pipeline/` — точные копии текущих файлов на 21 сентября 2026 года. Здесь нет готовых результатов нового исследования и новых пяти пайплайнов.

## Приоритет и полнота источников

Для новой сборки применяются текущие указания пользователя, `MASTER_PROMPT.md`, эта карта и затем исходные документы. Общий исторический план описывает направление развития; конкретные промпты и новые условия определяют исполняемые этапы. Утверждения и ссылки старых исследований проверяются заново, если используются как основание актуального решения.

В исходной папке есть отдельные промпты 00, 00A и 01–09. Этапы 10–19 присутствуют в общем плане, но отдельных действующих промптов с такими номерами в ней нет. Не обозначай их как скопированные документы. Полную рабочую цепочку доводки дают пять актуальных `ux-ui-pipelines/pipeline-*/PIPELINE.md` и их `prompts/`; упаковку для лендинга нужно добавить по требованиям мастер-промпта.

## Передача этапов

| Новая часть | Исходная основа | Вход → выход | Необходимая адаптация |
|---|---|---|---|
| Подтверждение идеи и отличий | 00 и 00A | Ответы и материалы → `CONFIRMED_INTENT.md` | Тема, обычный сценарий и отличия подтверждаются до исследования; готовый лендинг необязателен |
| Исследование | Новый модуль | Подтверждённая идея → 3 досье и доказательства | Субагент на сервис; фактический вход; подробный разбор функций и сценариев |
| Синтез и задание | Новый модуль | Досье + отличия → `FEATURE_MATRIX.md`, `APP_BRIEF.md` | Цельное приложение, прослеживаемость требований, границы демо |
| Product Context | 00 | `APP_BRIEF.md` → `PRODUCT_CONTEXT.md` | Автономное преобразование задания; второй продуктовый опрос не запускается |
| UX, сущности, IA, flows, states | 01–05 | Последовательные входы по исходным промптам → одноимённые артефакты | Сохранить frontend-объём; утверждённые отличия входят в покрытие |
| Реалистичные данные | 06 | Все предыдущие документы → `SYNTHETIC_DATASET.json` | Единые ID, подробные связанные данные; типичная вариативность до компоновки |
| Общий пул UX | 07 | Полный пакет → пять screens.pdf и карты страниц | Выполняется один раз при совместном запуске; методы автоматически выбирают UX-основу; код появляется только после ручного выбора финального дизайна |
| UX-проверка | 08 | Статичные экраны + требования → наблюдения по страницам | Может использоваться для выбора основы; отдельный аудит не является обязательным входом визуального этапа. Проверка итогового демо обязательна |
| Визуальная разработка и сборка | Пять UX/UI-пайплайнов, принципы 09 | Полный продуктовый пакет + выбранная основа → варианты, система и приложение | По пять design.pdf в каждом методе; общий ручной выбор одного из 25; детали выбранного PDF переходят в код одного приложения |
| Проверка, доводка, передача | verify/accept всех пяти методов | Приложение + требования → проверенный frontend и handoff | Общая рубрика и два раунда; проверка реальных действий выполняется только у приложения выбранной ветки |
| Пакет для лендинга | Раздел UI Asset Packaging общего плана + новый модуль | Проверенный frontend → снимки, фрагменты, маршрут демонстрации | Материалы снимаются с работающей версии, соответствуют её данным и состояниям |

## Стыковка с входами пяти UX/UI-методов

- `inputs/PRODUCT.md` содержит полный `APP_BRIEF.md`; `CONFIRMED_INTENT.md`, продуктовый контекст и исследования доступны рядом как источники.
- `inputs/RUN_SPEC.md` задаёт согласованный объём, платформу приложения, браузерную среду демонстрации, размеры, язык, контрольные задачи, общий ключевой экран, рубрику, режим `AUTO_UNTIL_DESIGN_SELECTION` и два раунда исправлений.
- `inputs/DATA.json` — побайтовая копия `SYNTHETIC_DATASET.json`; адаптер чтения может преобразовать представление в памяти, сохраняя ID и смысл. Отдельный набор данных не генерируется.
- Все исходные UX-документы, концепции и доказательства доступны каждому методу целиком. `MODEL.md` сопоставляет их ID с реализацией и не заменяет продуктовые факты новым пересказом.
- Источник исследования общий; выбор и адаптация визуальных приёмов самостоятельны. Структурные изменения допустимы как проектные решения метода при сохранении задач и обновлении зависимых flows/states/coverage.
- Для приложения мобильной платформы при необходимости собирается браузерное демо для лендинга, сохраняющее мобильные паттерны. Платформа продукта и среда воспроизведения фиксируются отдельно; native-сборка не становится неявным требованием.

## Конфликты, которые требуется устранить в рабочих копиях

| Исходное правило | Новое правило |
|---|---|
| Обязательны готовый лендинг и описание | Подтверждённая идея обязательна; лендинг используется при наличии |
| Прежние продуктовые интервью | Только начальное согласование; далее задание и отмеченные гипотезы |
| `WAITING_FOR_USER_SELECTION`, пользовательский выбор каждого экрана | Автоматический выбор UX-основ; общая галерея design.pdf → AWAITING_DESIGN_SELECTION → явный USER_SELECTED одного дизайна |
| Финальный статус зависит от визуального подтверждения пользователя | `READY_FOR_DEMO`, `REVISE` или `BLOCKED` по фактической проверке; принятие пользователем отмечается отдельно |
| Общий план требует production frontend и расширенный stress pass | Полный frontend согласованного демо и обычные состояния; техническая глубина определяется демонстрацией |
| Этап 09 повторяет уже выполненный поиск пяти направлений | Использовать его принципы и три образца внутри метода, без второй одинаковой ветки |
| README старых пяти методов требует десять сравнительных прогонов | Это отдельный эксперимент; в ALL создаются 25 дизайн-PDF и одно приложение после ручного выбора |
| Разные шкалы и лимиты в старых этапах | Одна рубрика 4/5 по каждому критерию; максимум два общих раунда исправлений на метод |

Изменения вносятся в полные тексты `pipelines/`, включая дочерние промпты, статусы, входы и выходы. Одна надстройка над конфликтующими текстами не считается адаптацией.

`PROMPT_VERSIONING_RULE.md` и шаблон сравнения сохранены как исходные служебные материалы. Их ссылка на прежнюю страницу сравнения не означает поручения менять другую папку или её сайт. При дальнейшем редактировании новых промптов сохраняй точные предыдущие версии и показывай полный diff соответствующей новой сборки.
