# 02 — Universal Domain Model

## Задача

Создай `DOMAIN_MODEL.md` — краткое описание сущностей продукта, их различий, связей и правил, необходимых для этапа Information Architecture.

## Входные материалы

Обязательны актуальные `PRODUCT_CONTEXT.md` и `UX_CONTEXT.md`. Прочитай их целиком. Если одного из файлов нет, остановись со статусом `INPUT_MISSING`; не заменяй его памятью.

Используй только материалы, разрешённые для текущего запуска. При противоречии продуктовые факты из `PRODUCT_CONTEXT.md` приоритетнее UX-выводов.

## Правила

- Работай автономно, без вопросов пользователю.
- Не придумывай функции, сущности и правила. Если без решения невозможно продолжить, выбери минимальную рабочую гипотезу и пометь её.
- Один термин должен обозначать одну сущность. Синонимы укажи как альтернативные названия, разные понятия не объединяй.
- Включай только сущности и связи в границах проектируемого продукта.
- Описывай только свойства, влияющие на распознавание, группировку, поиск, принадлежность, доступ или связь объектов.
- Не проектируй экраны, навигацию, компоненты, User Flows, подробные состояния, базу данных, API и техническую реализацию.

## Содержание `DOMAIN_MODEL.md`

### 1. Статус и источники

Укажи статус `FINAL — ready for Information Architecture`, использованные источники и границы модели.

### 2. Термины

Кратко зафиксируй неоднозначные понятия, различия и синонимы. Не создавай отдельный словарь очевидных терминов.

### 3. Сущности

Для каждой сущности укажи:

- стабильный ID и название;
- краткое определение;
- зачем она нужна пользователю;
- владельца или область принадлежности, если это влияет на доступ;
- свойства, необходимые для различения, группировки или поиска;
- связанные ID задач и требований из входных документов.

### 4. Связи и правила

Запиши связи в формате `сущность → отношение → сущность`. Укажи множественность только там, где она влияет на продукт. Зафиксируй принадлежность, вложенность, совместное использование и правила создания, объединения, разделения, переименования, архивирования или удаления только тогда, когда они меняют связи или доступность объекта.

### 5. Передача в Information Architecture

Укажи только факты, которые следующий этап обязан учесть:

- какие сущности пользователь должен находить напрямую;
- какие существуют только в контексте родительской сущности;
- по каким связям пользователь переходит между контекстами;
- какие группировки, области доступа и ограничения нельзя потерять.

### 6. Рабочие гипотезы

Оставь только гипотезы, способные изменить Information Architecture. Для каждой укажи затронутые сущности и решение, которое потребуется пересмотреть.

## Оформление и проверка

Результат — один `DOMAIN_MODEL.md` с заголовками и списками, без таблиц и диаграмм. Пиши сухо и кратко. Каждое сведение размещай один раз; далее ссылайся на ID. Не добавляй введение, вывод, пересказ источников, объяснение процесса и сведения, не нужные этапу Information Architecture. Удаляй пустые разделы.

Перед выдачей проверь, что все сущности и связи из проектируемого объёма учтены, термины не противоречат друг другу, гипотезы помечены, дубли и лишние детали удалены.
