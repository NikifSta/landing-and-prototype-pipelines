# 03 — Universal Information Architecture

## Задача

Создай `INFORMATION_ARCHITECTURE.md` — краткую структуру разделов, пользовательских точек назначения, навигации и размещения сущностей. Результат должен позволять проектировать User Flows, State Architecture и UX-концепции без повторного определения структуры продукта.

## Входные материалы

Обязательны актуальные `PRODUCT_CONTEXT.md`, `UX_CONTEXT.md` и `DOMAIN_MODEL.md`. Прочитай их целиком. Если одного из файлов нет или он не готов к следующему этапу, остановись со статусом `INPUT_MISSING`; не заменяй его памятью.

Используй только материалы, разрешённые для текущего запуска. При противоречии факты из `PRODUCT_CONTEXT.md` приоритетнее выводов остальных документов.

## Правила

- Строй архитектуру вокруг задач пользователя, частоты работы и необходимых переходов, а не вокруг перечня сущностей.
- Не делай каждую сущность самостоятельным разделом. Прямой доступ нужен объектам, с которыми пользователь работает независимо; зависимые объекты размещай в контексте родительских.
- У каждого раздела и точки назначения должна быть конкретная роль. Не создавай главную страницу или дашборд по умолчанию: если они нужны, укажи их задачу и состав.
- Сохраняй принадлежность, вложенность, доступ и связи из `DOMAIN_MODEL.md`.
- Основные задачи должны иметь понятные точки входа, продолжения работы и переходы между связанными контекстами.
- Работай автономно, без вопросов пользователю. Если источники не позволяют выбрать структуру, прими минимальную рабочую гипотезу и пометь её.
- Не добавляй функции, сущности и правила. Не проектируй последовательности User Flows, состояния, layout, компоненты, тексты интерфейса, визуальный стиль или техническую архитектуру.

## Содержание `INFORMATION_ARCHITECTURE.md`

### 1. Статус и источники

Укажи статус `FINAL — ready for User Flows and State Architecture`, использованные источники и границы проектирования.

### 2. Дерево информационной архитектуры

Покажи структуру вложенным Markdown-списком. Для каждого узла укажи:

- стабильный IA-ID;
- название;
- назначение;
- основные сущности или результаты;
- связанные ID задач и сущностей из входных документов.

Отделяй самостоятельные точки назначения от внутренних областей их содержимого. Не включай компоненты, действия, модальные окна и состояния.

### 3. Модель навигации

Зафиксируй:

- начальную точку и её роль;
- состав постоянной навигации;
- локальную навигацию внутри разделов;
- подтверждённые глобальные способы доступа;
- входы из внешних каналов и возврат из них, если они входят в продуктовый опыт.

### 4. Размещение сущностей

Для каждой ключевой сущности укажи её основное место, наличие прямого доступа, родительский контекст и допустимые альтернативные точки входа. Используй ID и не пересказывай описание сущности.

### 5. Сквозные переходы

Запиши только необходимые переходы между областями в формате `IA-ID → основание перехода → IA-ID`. Не описывай пошаговые сценарии.

### 6. Ограничения и рабочие гипотезы

Оставь только ограничения и гипотезы, которые меняют дерево, навигацию или размещение сущностей. Для каждой гипотезы укажи затронутые IA-ID и решение, которое потребуется пересмотреть.

## Оформление и проверка

Результат — один `INFORMATION_ARCHITECTURE.md`, без таблиц, диаграмм, введения и вывода. Пиши сухо и кратко. Каждое сведение размещай один раз; далее используй ID. Удаляй пустые разделы и всё, что не потребуется следующим этапам.

Перед выдачей проверь, что архитектура покрывает все задачи и сущности в заданных границах, не превращает модель данных в меню, не содержит скрытых разрывов между связанными областями и не подменяет следующие этапы.
