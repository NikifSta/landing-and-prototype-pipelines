# 05 — Universal State Architecture

## Задача

Создай `STATE_MATRIX.json` — компактную модель наблюдаемых frontend-состояний во всех утверждённых областях и сценариях. Зафиксируй, что видит пользователь, какие действия ему доступны и как интерфейс меняется после действия или видимого события.

Документ должен быть прямым входом и для Synthetic Data Preparation, использующего условия показа состояний, и для UX Concept Exploration и frontend-прототипирования, использующих области, состояния, действия и переходы. Обе задачи должны обходиться без повторного анализа предыдущих этапов и моделирования внутренней работы продукта.

## Входные материалы

Обязательны актуальные:

- `PRODUCT_CONTEXT.md`;
- `UX_CONTEXT.md`;
- `DOMAIN_MODEL.md`;
- `INFORMATION_ARCHITECTURE.md`;
- `USER_FLOWS.md`.

Прочитай их целиком. Если файла нет или он не готов к следующему этапу, верни только `{"status":"INPUT_MISSING","missing":["имя файла"]}`; не заменяй его памятью.

Используй только материалы текущего запуска. Сохраняй термины, ID, границы, IA и маршруты. При противоречии продуктовые факты приоритетнее производных решений; несовместимость фиксируй как `issue`.

## Правила

- Моделируй только интерфейсы из IA и подтверждённые внешние точки взаимодействия в границах продукта.
- Создавай отдельное состояние, только если меняются видимое содержание, статус, доступные действия или следующая реакция интерфейса.
- Покрой применимые `ready`, `loading`, `processing`, `empty`, `success`, `partial`, `error` и `blocked` состояния. Не добавляй тип состояния, если он не нужен конкретной области или действию.
- Объединяй ошибки с одинаковым отображением и восстановлением. Не перечисляй технические причины сбоев.
- Для каждого действия пользователя и видимого автоматического события укажи переход между состояниями интерфейса. Внутренние этапы обработки не моделируй.
- Формулируй `condition` как факты, по которым следующий этап сможет создать fixture для показа состояния в прототипе. Сами синтетические данные не создавай.
- Ограничения доступа описывай только через видимое объяснение и доступные действия, без механизма проверки прав.
- Работай автономно. Если без решения модель неполна, выбери минимальную рабочую гипотезу и зафиксируй её в `issues`.
- Не проектируй layout, компоненты, точные тексты, визуальный стиль и анимацию. Не описывай backend-состояния, API, алгоритмы, авторизацию, хранение и инфраструктуру.

## Структура `STATE_MATRIX.json`

Верхний уровень:

- `status`: `FINAL — ready for Synthetic Data Preparation and Prototyping`;
- `sources`: использованные файлы;
- `ui_areas`: области интерфейса и их состояния;
- `issues`: только гипотезы и противоречия, способные изменить данные или прототип. Пустые необязательные поля не добавляй.

Каждая `ui_area` содержит:

- `id`, `name`;
- `refs`: массив связанных ID из входных документов;
- `default_state`;
- `states`;
- `transitions`.

Каждое состояние содержит:

- `id`, `kind`;
- `condition`: факты, необходимые для показа состояния;
- `visible`: массив наблюдаемых результатов, статусов или ограничений;
- `available_actions`: массив смысловых действий;
- `blocked_actions`: только значимые недоступные действия в формате `{"action":"...","visible_reason":"..."}`.

Каждый переход содержит `from`, видимое `event` и `to`. Используй ссылки на ID вместо повторного описания.

Каждый `issue` содержит `id`, `type`, `refs`, принятое `decision` и его `impact`.

## Оформление и проверка

Результат — только валидный `STATE_MATRIX.json`, без Markdown и комментариев. Пиши кратко; каждое сведение размещай один раз, пустые поля удаляй.

Перед выдачей проверь внутренне, что покрыты все frontend-области, действия и развилки `USER_FLOWS.md`; для каждого состояния определены видимый смысл, доступные действия и условия показа; переходы интерфейса не имеют необъяснённых разрывов; дубли, backend-логика и сведения, не нужные Synthetic Data Preparation или прототипированию, удалены. Не добавляй отчёт о проверке.
