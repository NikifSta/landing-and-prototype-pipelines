# 06 — Universal Synthetic Data Preparation

## Задача

Создай `SYNTHETIC_DATASET.json` — единый согласованный набор правдоподобных синтетических данных для всех UX-концепций и frontend-прототипов. Он должен реализовать сущности, связи, пользовательские сценарии и условия показа состояний, чтобы следующий этап использовал одни и те же данные без их изобретения и повторного анализа продукта.

## Входные материалы

Обязательны актуальные:

- `PRODUCT_CONTEXT.md`;
- `UX_CONTEXT.md`;
- `DOMAIN_MODEL.md`;
- `INFORMATION_ARCHITECTURE.md`;
- `USER_FLOWS.md`;
- `STATE_MATRIX.json`.

Прочитай их целиком. Если файла нет или он не готов к следующему этапу, верни только `{"status":"INPUT_MISSING","missing":["имя файла"]}`; не заменяй его памятью.

Используй только материалы текущего запуска. Сохраняй термины, ID, ограничения, отношения и границы продукта. При противоречии продуктовые факты приоритетнее производных решений; несовместимость фиксируй как `issue`.

## Правила

- Создавай только вымышленные данные без сведений о реальных людях и компаниях.
- Используй один канонический набор записей со стабильными ID, ссылками, хронологией и взаимно согласованными значениями. Переиспользуй записи между сценариями вместо создания независимых примеров для каждого экрана.
- Покрой все отображаемые сущности и связи из `DOMAIN_MODEL.md`, все основные сценарии `USER_FLOWS.md` и каждое условие показа из `STATE_MATRIX.json`.
- Для каждого сценария укажи записи и fixtures, необходимые для его прохождения. Для каждого состояния создай fixture, который однозначно выполняет его `condition`.
- В fixture ссылайся на канонические записи. Добавляй локальный `context` только для видимого временного состояния, фильтра, запроса, ошибки или ограничения, которое нельзя выразить канонической записью.
- Наполняй данные правдоподобным предметным содержанием: конкретными названиями, именами, датами, статусами, текстами и значениями в языке и контексте продукта. Не используй lorem ipsum, технические заглушки и пояснения для дизайнера.
- Создай примерно втрое больше канонических записей нормального рабочего диапазона, чем минимально требуется для однократного покрытия flows и states. Дополнительные записи должны показывать типичную вариативность, а не повторять один шаблон. Экстремальные stress-варианты относятся к отдельному этапу Lived-in & Edge-case Pass.
- Соразмеряй детализацию записи с реальным объёмом объекта и его контекстом. Связанные данные должны образовывать полноценный правдоподобный пример: например, у встречи длительность, участники, повестка, обсуждённые темы, расшифровка, итоги и задачи, если они предусмотрены источниками, согласованы между собой и наполнены в реалистичном объёме.
- Включай только данные, которые отображаются во frontend или определяют наблюдаемое состояние. Не проектируй интерфейс, компоненты, layout, визуальный стиль, анимацию, API, backend, алгоритмы и инфраструктуру.
- Работай автономно. Если без решения набор данных неполон, выбери минимальную согласованную гипотезу и зафиксируй её в `issues`.

## Структура `SYNTHETIC_DATASET.json`

Верхний уровень:

- `status`: `FINAL — ready for UX Concept Exploration`;
- `sources`: использованные файлы;
- `context`: язык, locale, timezone и фиксированный `reference_time`;
- `records`: канонические записи, сгруппированные по ID сущностей из `DOMAIN_MODEL.md`;
- `scenario_fixtures`: данные для прохождения пользовательских сценариев;
- `state_fixtures`: данные и контекст для показа состояний;
- `issues`: только гипотезы и противоречия, способные изменить данные или прототип. Пустые необязательные поля не добавляй.

Каждая каноническая запись содержит `id`, только предусмотренные предметной моделью поля и ссылки на связанные записи по ID.

Каждый `scenario_fixture` содержит:

- `id`;
- `flow_refs`;
- `record_refs`;
- `state_fixture_refs`.

Каждый `state_fixture` содержит:

- `id`;
- `ui_area_ref`, `state_ref`;
- `record_refs` и/или `context`: только записи и значения, необходимые для выполнения `condition`.

Каждый `issue` содержит `id`, `type`, `refs`, принятое `decision` и его `impact`.

## Оформление и проверка

Результат — только валидный `SYNTHETIC_DATASET.json`, без Markdown и комментариев. Пиши компактно; не дублируй записи и сведения, используй ссылки по ID, пустые поля удаляй.

Перед выдачей проверь внутренне, что все ссылки разрешаются; связи, ограничения и хронология согласованы; каждый основной flow и каждое состояние имеют fixture; данные достаточны для сравнения UX-концепций на одинаковом содержании; дубли, backend-детали и сведения, не нужные следующему этапу, удалены. Не добавляй отчёт о проверке.
