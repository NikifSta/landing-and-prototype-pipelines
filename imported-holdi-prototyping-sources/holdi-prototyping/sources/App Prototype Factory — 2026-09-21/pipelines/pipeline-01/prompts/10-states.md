# 10 — Спроектировать наблюдаемые состояния

**Исполнитель:** UX-дизайнер frontend-состояний

**Вход:** APP_BRIEF, PRODUCT_CONTEXT, UX_CONTEXT, DOMAIN_MODEL, INFORMATION_ARCHITECTURE, USER_FLOWS.

**Действия**

Создай только наблюдаемые состояния областей интерфейса. Отдельное состояние нужно при изменении видимого содержимого, статуса, доступного действия или следующей реакции. Из ready/loading/processing/empty/success/partial/error/blocked используй применимые; технические причины и редкие исключения не добавляй ради полноты.

STATE_MATRIX.json — валидный JSON. Верхний уровень: status, sources, ui_areas, issues при наличии. Область: id, name, refs, default_state, states, transitions. Состояние: id, kind, condition (проверяемые факты для fixture), visible (наблюдаемые результаты), available_actions; blocked_actions при необходимости как action/visible_reason. Переход: id, from, event, to. Issue: id, type, refs, decision, impact.

Для каждого действия и видимого автоматического события есть переход. Ошибки с одинаковым отображением и восстановлением объединяй. Доступ описывай через объяснение и действия, без серверной проверки. Сами записи и fixtures создаёт следующий этап.

**Выход и потребитель:** STATE_MATRIX.json → генератор данных и frontend; status FINAL.

**Готовность:** JSON разбирается; ID и ссылки разрешаются; состояния/переходы покрывают flows; для каждого состояния понятен fixture и способ показать его.

**Возврат:** Разрыв маршрута → 09; условие/видимая реакция → здесь. Передай неисправимое противоречие оркестратору, не создавай скрытую backend-модель.
