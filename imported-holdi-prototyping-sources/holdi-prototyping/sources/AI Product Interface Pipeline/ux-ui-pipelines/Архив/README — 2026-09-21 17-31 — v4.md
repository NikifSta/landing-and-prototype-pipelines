## Протокол сравнения

Пайплайны готовы к запуску; результаты конкретного продукта ещё не получены. Победителя нет. Каждый подход самодостаточен, правила его исполнения находятся в PIPELINE.md. Сейчас runs/ пусты; результаты создаются только при запуске.

### 1. Заморозить условия

До эксперимента подготовь единый пакет `PRODUCT.md`, `RUN_SPEC.md`, `DATA.json` и приложенные исходные материалы. Подготовительные файлы можно хранить в `pipeline-01/runs/<comparison-id>-setup/inputs/`; setup не считается запуском. Скопируй одинаковые байты в inputs каждого запуска, сохрани хеши. Пайплайны затем работают только со своими копиями.

В RUN_SPEC зафиксируй:

- Продукт, аудиторию, весь охват, продуктовые ограничения, контрольные задачи и наблюдаемые результаты; одинаковые данные и способ сброса.
- Платформы, версии, размеры экранов, включая минимальные, ввод, язык, шрифтовую среду и применимые проверки доступности.
- Один пул моделей и инструментов, два раунда исправлений; в каждом запуске пользователь выбирает один из пяти вариантов одинакового ключевого экрана на одинаковых данных, затем подтверждает итог. Фактические время, токены и стоимость учитывай для сравнения; недоступные измерения — «неизвестно».
- Один стандарт поиска: категория + та же платформа + год запуска, рейтинги/подборки/премии приложений, доказательство года работы, реальные экраны, 1–2 совместимых референса на платформу. Поиск каждый выполняет самостоятельно; его расход учитывается в сравнении.
- Общую рубрику ниже и одинаковые калибровочные примеры уровня 4, уже соответствующие целевой платформе. Они задают планку исполнения и выдаются всем, но не заменяют обязательный самостоятельный поиск продуктовых референсов.

Измеряй активное elapsed без ожидания пользователя. Токены/стоимость всех агентов, кандидатов и исправлений суммируются. Масштаб эксперимента не уменьшается задним числом ради прохождения. При изменении существенного входа создай новую версию условий и заново выполни затронутые запуски всех подходов; разные версии не смешивай.

### 2. Выполнить минимум десять запусков

По два независимых запуска каждого подхода: чистый контекст, новая R, исходные данные и отсутствие доступа к решениям других запусков. Используй разные run-id. Исправления и пять внутренних вариантов каждого пайплайна не являются отдельными запусками.

Порядок запусков случайно перемешай, среду и версии закрепи. Независимые задачи можно выполнять параллельно без общей записи в исходники; учитывай суммарные ресурсы и ограничения среды. Если пользователь уточнил продукт, одинаково обнови входы всех подходов. Измеряй время ожидания пользователя отдельно от активной работы. Не подсказывай одному автору идеи из другого запуска.

Для каждого из пяти вариантов отдельно пройди последовательность H1–H4: три первые гипотезы отклони с конкретным основанием, четвёртую разработай по изученным референсам и проверь. Это пять самостоятельных цепочек поиска, а не общий отсев трёх из пяти. Поиск кандидатов в референсы и все гипотезы входят в затраты основного прохода.

Перед развитием дизайна каждого запуска предъяви все пять вариантов ключевого экрана по правилам его PIPELINE. Получи отдельный выбор пользователя; до него статус — `WAITING_FOR_USER_SELECTION`. Для совместного предъявления сгруппируй варианты по пайплайнам и сохрани номера внутри групп.

### 3. Применить единые gates

1. Полнота: покрыты все сценарии охвата и значимые состояния.
2. Работоспособность: контрольные задачи дают требуемые локальные изменения и видимый результат, включая связанные представления.
3. Среда и доступность: пройдены обязательные проверки PIPELINE на целевой платформе, включая минимальный размер. Непроверенное не считается успехом.
4. UX и визуальное исполнение: отдельно UX, композиция, типографика, цельность, детали — каждый критерий ≥4 из 5; нет открытых дефектов, мешающих задаче, чтению или управлению.

Шкала: 1 — мешает задаче; 2 — крупные дефекты; 3 — работает, но неровно; 4 — законченно и сопоставимо с отобранными эталонами исполнения; 5 — исключительно убедительно с конкретными основаниями. Калибровка общая, оценка каждой реализации подкреплена экраном и наблюдением. Средний балл не компенсирует провал gate. Достижение «уровня Apple» не объявляется по одной автоматической оценке.

### 4. Сравнить вслепую

Оркестратор назначает случайные метки результатам. Карта соответствий и итоговая форма находятся в `pipeline-01/runs/<comparison-id>-comparison/`; результаты самих запусков остаются внутри соответствующих пайплайнов. В материал для reviewer включи анонимные запускаемые результаты, одинаковые задачи/критерии/калибровку, выбранные референсы без названий подходов. Скрой авторов, названия пайплайнов, гипотезы, прежние оценки и затраты до завершения оценки качества. Рандомизируй порядок предъявления.

Reviewer сначала выполняет задачи, затем смотрит одинаковые экраны/состояния и оценивает качество. Это экспертная или агентная проверка, не исследование с реальными пользователями. Участие целевых пользователей, если предусмотрено, одинаково для всех. Пользователь подтверждает финальный визуальный выбор после предъявления конкретных результатов; разрешён отказ всем.

### 5. Заполнить компактную форму

Одна строка на запуск; доказательства — ссылки на его REVIEW и скриншоты.

| Метка / run-id | Gates: охват / функция / доступность / визуал | UX / композиция / типографика / цельность / детали | Elapsed / активное время | Токены / стоимость | Раунды / вмешательства | Доказательства | Выбор пользователя |
|---|---|---|---|---|---|---|---|
| Заполнить после запуска | pass / fail / не проверено | 1–5 по каждому | Фактические значения | Значения или неизвестно | Количество | Ссылки | Ожидается / принят / отклонён |

После раскрытия меток сведи по подходу: прохождения из двух, медианы пяти оценок и их диапазоны, суммарные ресурсы, причины возвратов. Два запуска — минимальная проверка устойчивости, не статистическое доказательство надёжности.

### 6. Выбрать по результатам

Сначала исключи провалы gates. Для рекомендации устойчивого подхода нужны два прошедших запуска. Среди прошедших сравни UX и четыре визуальных критерия; превосходство обоснуй задачами и наблюдениями. При сопоставимом качестве предпочти более устойчивый и менее затратный вариант. Если один результат лучше по качеству, другой дешевле, покажи компромисс пользователю; не назначай скрытые веса задним числом.

При недостатке измерений не делай вывод об экономичности. Если оба запуска не прошли ни у одного подхода, победителя нет: причины исправляются в новой версии эксперимента. Вывод по одному продукту распространяется только на этот продукт, платформу, модели и число раундов исправлений.
