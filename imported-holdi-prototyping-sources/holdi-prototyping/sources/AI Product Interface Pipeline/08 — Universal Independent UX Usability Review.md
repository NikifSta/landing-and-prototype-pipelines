# 08 — Universal Independent UX Usability Audit

## Задача

Проведи пять отдельных строгих usability-аудитов UX-концепций этапа 07. Оркестратор назначает каждому прототипу независимого аудитора. Каждый аудитор видит только свой вариант и оценивает, понятен ли интерфейс и удобно ли выполнять предусмотренные для лендинга задачи.

Аудиторы не сравнивают концепции, не изменяют прототипы и не проектируют новый вариант. Оркестратор только собирает результаты.

## Границы проверки

Проверяй только разделы и сценарии в объёме интерфейса для лендинга, зафиксированном в `PRODUCT_CONTEXT.md` и остальных входах. Не требуй интерфейсы и функции за его пределами.

Прототип является frontend-имитацией. Backend, база данных, настоящая авторизация, AI-вычисления, отправка сообщений и внешние интеграции не требуются. Они могут быть представлены локальным состоянием, fixtures, подготовленными ответами и имитацией задержки. Перезагрузка страницы может сбрасывать данные.

Каждое видимое действие внутри выбранного объёма должно давать правдивый наблюдаемый результат. Аудитор проверяет этот результат, но не способ технической реализации.

## Входные материалы

Обязательны актуальные:

- `PRODUCT_CONTEXT.md`;
- `UX_CONTEXT.md`;
- `DOMAIN_MODEL.md`;
- `INFORMATION_ARCHITECTURE.md`;
- `USER_FLOWS.md`;
- `STATE_MATRIX.json`;
- `SYNTHETIC_DATASET.json`;
- результат этапа 07: пять запускаемых прототипов с `CONCEPT.md` и `COVERAGE.json`.

Если отсутствует продуктовый источник, верни только `{"status":"INPUT_MISSING","missing":["имя файла"]}`. Неработающий прототип пометь как `INCOMPLETE`; остальные проверки продолжи.

## Запуск аудиторов

Запусти ровно пять аудиторов параллельно — по одному на `concept-01` … `concept-05`. Каждый читает все продуктовые источники целиком и получает только назначенную концепцию. Не передавай ему другие прототипы, их описания, аудиты или сравнительный обзор.

Все аудиторы используют одинаковые задачи, viewport и условия. Перед каждой задачей прототип возвращается в исходное состояние. Проверяется работающий интерфейс; чтение кода не заменяет взаимодействие.

До первого прохождения аудитор не читает `CONCEPT.md` и `COVERAGE.json`. После него эти файлы используются для проверки гипотезы и заявленного покрытия.

## Проверка одного прототипа

Аудитор:

1. Фиксирует первое понимание продукта, текущего состояния, доступных объектов и следующего действия.
2. Проходит каждый flow выбранного объёма через указанные точки входа и fixtures.
3. Воспроизводит влияющие на сценарии состояния из `STATE_MATRIX.json`.
4. Проверяет обнаруживаемость действий, понятность терминов и структуры, обратную связь, последствия действий, количество необходимых шагов, сохранение контекста, предотвращение ошибок, восстановление, последовательность поведения, читаемость и базовое управление с клавиатуры.
5. Повторяет основные задачи и проверяет, становится ли работа быстрее без запоминания скрытых путей.

Для AI, поиска и внешних сервисов достаточно подготовленной frontend-имитации на канонических данных. Не требуй произвольных AI-ответов, реальной отправки или синхронизации.

## Классификация результатов

Разделяй два типа недостатков:

- `PROTOTYPE_GAP` — предусмотренное взаимодействие невозможно проверить, потому что frontend-имитация не запускается, не меняет наблюдаемое состояние или заменена техническим fixture;
- `USABILITY_ISSUE` — сценарий работает достаточно для проверки, но пользователь не понимает его, не находит действие, ошибается или тратит лишние усилия.

Отсутствие понятного пути к действию внутри выбранного объёма — `USABILITY_ISSUE`. Наличие действия без имитации результата — `PROTOTYPE_GAP`.

Для `PROTOTYPE_GAP` ставь flow `NOT_TESTABLE`. Он не считается usability-проблемой и не снижает оценку понятности или удобства. Для `USABILITY_ISSUE` используй:

- `BLOCKER` — ключевая задача не завершается либо пользователь теряет результат или контроль;
- `MAJOR` — вероятны остановка, существенная ошибка или повторяющееся серьёзное затруднение;
- `MINOR` — задача завершается, но есть локальная неясность или лишнее усилие.

Каждый вывод подтверждай: `flow/state ID`, исходное условие, действие, ожидаемое и наблюдаемое поведение, влияние на пользователя.

## Вердикт и рекомендации

Отдельно оцени:

- `Полнота прототипа: COMPLETE / PARTIAL / INCOMPLETE`;
- `Понятно: YES / PARTLY / NO / INCONCLUSIVE`;
- `Удобно: YES / PARTLY / NO / INCONCLUSIVE`;
- `UX-вердикт: PASS / CONDITIONAL / FAIL / INCONCLUSIVE`.

`PASS` означает отсутствие `BLOCKER` и `MAJOR`; `CONDITIONAL` — наличие `MAJOR` без системного провала; `FAIL` — проверяемые ключевые сценарии имеют `BLOCKER` или системно неудобны. `INCONCLUSIVE` ставится, если ключевые сценарии получили `NOT_TESTABLE`. Неполный прототип сам по себе не означает плохой UX.

Для каждого `PROTOTYPE_GAP` укажи минимальный наблюдаемый frontend-результат, необходимый для повторного аудита, и критерий приёмки. Для каждого `USABILITY_ISSUE` укажи требуемый пользовательский результат после исправления и критерий приёмки. Не предписывай backend, код или визуальный стиль.

## Результат

Каждый аудитор создаёт `ux-audits/concept-XX/UX_USABILITY_AUDIT.md`:

1. Полнота, количество проверенных и `NOT_TESTABLE` flows, понятность, удобство и UX-вердикт.
2. Результат каждого flow: `PASS / FRICTION / FAIL / NOT_TESTABLE` с причиной.
3. `PROTOTYPE_GAP` с требованием к frontend-имитации и критерием приёмки.
4. `USABILITY_ISSUE` по серьёзности с рекомендацией и критерием приёмки.
5. Подтверждённые сильные решения.
6. Готовность к UX Convergence: `READY / REVISE / REJECT`.

`REJECT` допустим только при системном UX-провале проверяемой концепции. Неполный прототип получает `REVISE` и повторный аудит.

Оркестратор создаёт `ux-audits/AUDIT_OVERVIEW.md` только с путями к пяти аудитам, их отдельными оценками полноты и UX и готовностью к UX Convergence. Он не ранжирует варианты и не меняет заключения аудиторов.

Не включай пересказ продукта, описание процесса, комплименты и повторяющиеся замечания. Пиши коротко; каждый вывод связывай с наблюдением.
