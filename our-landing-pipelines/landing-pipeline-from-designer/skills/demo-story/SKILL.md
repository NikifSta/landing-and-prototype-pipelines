# Демо-история

Одна правдоподобная вымышленная ситуация, из которой берут данные **все** экраны, сцены и промпты медиа. Результат — `projects/<slug>/04-demo-story.md`.

## Пути
- **Корень плагина** — два уровня выше этого файла (`skills/demo-story/` → `../../`): `references/`, `CLAUDE.md`. Команды `node scripts/…` в этом скилле означают `node "<корень плагина>/scripts/…"`; запускай их **из рабочей папки пользователя** (там лежат `projects/` и по желанию `.env`; скрипты сами читают `.env` рабочей папки и корня плагина). `references/`, `templates/`, `schemas/` лежат в корне плагина, пути `projects/<slug>/…` — в рабочей папке. Не переходи в корень плагина и не создавай проекты внутри него.
- **Проект** — `projects/<slug>/` в текущей рабочей папке; slug — имя папки проекта, аргумент `$ARGUMENTS` (не передан — первый проект, где отмечен story, но не demo-story).
- Нет `03-story.md` — сначала выполни story.

## Шаги

### 1. Вход
Прочитай `03-story.md` (для каждой секции — «что показываем»), `01-intake.json` (аудитория, рынок, язык), `open-questions.md` (если есть), `02-research/spec.md` (какие экраны и данные показывают аналоги). Составь список **всех** мест, где нужны данные, по тому, что описано в «что показываем» сценария: hero, сцены, карточки, списки, формы, уведомления. Макетов ещё нет (этап `/ui` позже), поэтому данных столько, сколько нужно, чтобы показать описанное в сценарии: типично 3–6 людей, 5–8 строк в списках. Для каждого компонента запиши и **начальное состояние** (заглушки «считаю…», «собираю итоги…»), чтобы ни один компонент не был пустым.
Если сцена сценария нелогична (например, «тот же заказ» показан там, где у системы данных быть не может), не меняй сценарий молча: выбери разумное решение и запиши его в раздел «Замечания к сценарию» истории.

### 2. Придумай историю
- Одна ситуация, подходящая **типу продукта**: для B2B — компания (название, чем занимается, город) и сотрудники; для потребительского продукта — семья или человек и их окружение (дети, мастера, тренеры); для маркетплейса — две стороны (кто ищет и кто предлагает). 3–6 людей (имя, роль, инициалы для аватаров), даты и время, предмет учёта (что считается: заказы, уроки, платежи, тренировки) и расписание вместо «меню», если меню нет.
- Название компании, город и предыстория нужны только для согласованности данных. На страницу они не выходят: в заголовках, подписях и пояснениях только название продукта («[Продукт]» до этапа brand), ситуация описана абстрактно.
- Бренд вымышленной компании допустим **только внутри экранов** (приложение, карточки, уведомления), где без него экран не читается. В заголовках, подписях, пояснениях и кнопках страницы его нет. Реальные компании, сервисы, агрегаторы и конкуренты по имени не используются (если `01-intake.json` не требует иначе); вместо них — общие слова («сервис», «агрегатор»).
- Телефоны, номера заказов и подобные идентификаторы вымышлены и частично скрыты (`+7 900 ··· 00-12`), реальных номеров нет.
- Одна «сегодняшняя» дата, все события относительно неё; периоды «за 12 месяцев» заканчиваются до этой даты, прошлое — прошлое, будущее — будущее.
- Имена и реплики на языке аудитории (`language`), правдоподобные для рынка.

### 3. Данные для каждой секции
Для каждой секции плана выпиши конкретику: сообщения, задачи, имена, суммы, даты, проценты, статусы. Один и тот же человек, заказ или сумма в разных сценах называется и считается одинаково. Данные должны читаться **внутри интерфейса без предыстории**. Не добавляй данные, которые не пойдут ни в один экран.
Числа считай не «на глаз»: меню, цены и тарифы заведи один раз и бери оттуда; итоги выводи формулой.
- **Связи чисел.** Выпиши, какие числа связаны формулой (одна сумма встречается в нескольких сценах, итог складывается из частей) — они должны совпадать везде; остальные (число заказов у гостя, размер базы) — независимые демонстрационные значения, формулой не выводятся.
- **Округление.** Подбирай параметры так, чтобы проценты и итоги получались целыми (рубли без копеек).
- **Периоды.** Помесячные данные делай неровными и правдоподобными (сезонность: рост перед праздниками, спад летом) и одной строкой объясни, откуда неровность.
- Параметры, которых нет в `01-intake.json` и сценарии (например, «доля вернувшихся гостей»), вводи только если сцена без них не работает, и помечай как демонстрационные.

### 4. Проверка чисел
Перед сохранением перепроверь арифметику выполнением расчёта (например, `node -e`, он есть на любой системе), а не в уме:
- суммы по периодам равны годовой/общей сумме;
- проценты и комиссии пересчитываются в рубли по тем же параметрам;
- составные суммы (заказ, счёт, урок, тариф) собираются из исходных позиций; даты и дни недели совпадают с календарём (проверь в `node -e` через `new Date("ГГГГ-ММ-ДД").toLocaleDateString("ru-RU", {weekday: "long"})`).
Нашёл расхождение — исправь данные, а не подгоняй подписи.

### 5. Честность демонстрационных данных
- Значения параметров (проценты, чеки, комиссии) — демонстрационные; один раз пометь это в разделе «Расчёты» («демонстрационные значения, не факты о рынке»).
- Настоящих клиентов, отзывов, рейтингов и цифр рынка не придумывай и не выдавай придуманное за факт. Нужное из `open-questions.md` оставь заглушкой.

### 6. Сохранение
`04-demo-story.md` с фиксированными разделами в таком порядке:
1. `# Демо-история`: правила (одна история, названия вне страницы), внутренняя легенда, «сегодняшняя» дата.
2. «Люди, бренд и меню» (таблицы).
3. «Расчёты»: параметры, таблицы с итогами, «Связи чисел».
4. Данные по каждой сцене в порядке секций сценария, у каждой — начальное состояние.
5. «Произвольные решения»: что выбрано без исходных данных (название, акции, значения параметров, сезонность).
6. «Замечания к сценарию» (если были).
7. «Что нельзя» (реальные названия, расхождение чисел и дат, вынос бренда выдуманной компании в заголовки страницы).
Отметь в `checklist.md` пункт 4 (если строка уже есть с другим описанием, замени её целиком): `- [x] 4. demo-story — \`04-demo-story.md\` — <дата>`.

## Итог для пользователя
Коротко: сквозной персонаж и ситуация, главные числа (итоги), раздел «Произвольные решения» одной строкой каждое (название, акции, значения параметров), чтобы пользователь подтвердил или поправил.

## Проверка перед завершением
- Каждая секция сценария с интерфейсом или сценой имеет данные и начальное состояние.
- Числа проверены расчётом; даты и дни недели правильные.
- Нет реальных компаний и конкурентов по имени; на страницу выходит только название продукта.
- Нет выдуманных клиентов, отзывов и рыночных цифр, поданных как факт.
- Чеклист отмечен.

## Правки сценария
Если расчёты демо-истории не сходятся с числами в `03-story.md` (остаток, итог, процент), правь `03-story.md` и записывай расхождение в раздел «Замечания к сценарию» этого этапа; числа демо-истории считай скриптом (`node -e`), даты и дни недели проверяй им же.
